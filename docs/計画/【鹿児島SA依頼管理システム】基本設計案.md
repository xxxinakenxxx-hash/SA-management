# 【鹿児島SA依頼管理システム】基本設計案

作成日：2026-10-20
状態：**設計案・未承認**（承認済み正本ではない）
対象：鹿児島営業所からSAへの依頼管理。実装担当：Claude Code。

注意：既存営業AIメモの現行本番API・DB・認証処理は未照合。記載する連携案を現行実装済みと扱わない。

## 1. 目的と境界

鹿児島の営業担当者が営業AIメモから出したSA依頼を、鹿児島の複数のSA担当者が共有し、引受・担当変更・進捗・質問回答・成果物返却まで扱う独立した業務システムを設ける。既存の全社共通営業AIメモは**原則変更しない**。

- 営業AIメモ：音声・テキスト入力とSA依頼の既存保存処理を担う。
- SA-management：依頼の取り込み、SA業務処理、担当・進捗・スレッド・成果物を管理する。
- SA利用者：Windowsの専用画面で業務を完結させる。Gmailを手動で開かずに質問や結果通知を送る。
- 営業利用者：スマートフォン対応の別画面で質問に回答し、依頼の状態・返却結果を見る。既存営業AIメモ内にスレッド画面を追加しない。
- 鹿児島対象者以外が閲覧・操作できないようにする。具体的な本人確認・地域判定は基本設計の未決事項。

## 2. 既存システムとの接続境界（要実コード照合）

既存会話での採用方針は、営業AIメモが「SA案件」「SA依頼」の表現をSA依頼として扱い、保存タイトルを「SA依頼｜内容」とし、分類値を`sa_case`とするもの。ただし**現行本番コード・シートでの実装有無、実際の列名、登録ID、利用者識別子は未確認**。

取り込みの候補手順：
1. 営業AIメモ内の既存記録から対象レコードを抽出する。
2. 元レコードIDをキーに同一依頼の二重取り込みを防止する。
3. 鹿児島所属の依頼者であることを確認した後、SA-managementの依頼データに登録する。
4. 営業へSA管理画面の当該依頼に移動できる通知を自動送信する。直接リンクは認可確認後にのみ内容を表示する。

取り込み方式（既存保存処理からの連携、GASの定期取得等）、反映時間、失敗時の再試行、古いレコードの扱いは設計決定前に既存処理を調査する。既存GASコードに変更が必要な場合は別途変更案と承認を要する。

## 3. 利用者・権限（案）

| 操作者 | 許可する業務 |
| --- | --- |
| 鹿児島営業担当者 | 自分の依頼閲覧、質問回答、スレッド送信、返却成果物閲覧 |
| 鹿児島SA担当者 | 対象地域の依頼一覧閲覧、担当引受・変更、進捗更新、質問送信、ファイル追加、完了返却 |
| 管理権限者 | 担当者マスターや例外処理の運用（必要性・範囲は未確定） |

各APIでログイン済みの本人・所属・対象依頼権限を照合する。画面の非表示やURLを知っていることだけを認可条件にしない。既存のユーザーマスターの参照先・識別子・権限情報は未確認。

## 4. 業務フロー（案）

1. **受付**：営業AIメモ側でSA依頼を記録 → SA管理側へ一意に登録 → 複数SA担当者の共通一覧へ表示。
2. **担当**：未担当の依頼をSA担当者が「担当する」で引受。誰がいつ引き受けたか履歴を残す。担当変更時も旧担当を履歴で保持。
3. **作業**：SAは対応中の依頼を処理し、必要なら営業に質問を投稿。**投稿が成功した時点**で営業回答待ちにする。
4. **回答**：営業は通知リンクから本人認証後、該当スレッドに回答。SA側に新着を表示し、再開できる。回答だけで自動的に完了しない。
5. **成果物**：SAがPDF等を所定のDrive保管先へ登録し、依頼と関連付ける。閲覧権限は当該依頼の許可利用者に限る。
6. **完了**：SAが返却コメントと必要な成果物を確定して完了登録。営業に自動通知し、営業用画面から完了内容を閲覧可能とする。
7. **履歴**：担当変更、状態変更、質問・回答、ファイル登録、完了、エラー等を記録する。

状態は原則 `未担当 → 対応中 → 営業回答待ち → 完了`。ただし回答待ち→対応中への復帰、担当変更、再オープンの可否は要確認。状態更新はサーバー側で許可遷移を検査する。

## 5. 画面（既存モックを採用）

### SA向け：Windows・3カラム
- 左：依頼一覧、状態・担当・未読・検索／絞込。
- 中央：依頼詳細、引受・担当変更・状態操作、作業メモ、完了登録。
- 右：営業とのスレッド、ファイル・成果物、履歴の確認。
- SA側の日常業務は原則この画面内で完結。既存モック4ファイルは基本設計段階で変更しない。

### 営業向け：スマートフォン
- 自分の依頼一覧／通知からの該当依頼表示。
- 状態確認、質問と回答、完成した成果物の参照。
- 認証済みでも他営業の依頼を表示しない。

### デザイン
情報設計は現行モックを基準とし、AIサービスのような洗練されたUIは機能実装後にブラッシュアップする。

## 6. 技術責務（採用方針と検証課題）

| 構成 | 担当 |
| --- | --- |
| GAS | 認可、依頼・メッセージ・状態更新、通知制御、Driveアクセス、既存データ連携 |
| Google Sheets | 依頼、メッセージ、ファイル参照、状態変更・操作履歴等のデータ |
| Google Drive | PDFその他の成果物（本番データはGitHubへ入れない） |
| HTML/CSS/JavaScript | SA画面、営業画面 |
| PWA | Windows向けの使い勝手と通知導線の候補 |

**重要な実現性確認**：
- GitHub Pages等の独立オリジンからGASへ安全に接続できるか、CORS・セッション・認証・デプロイ権限を実際に検証する。できない場合は無断で別基盤へ切り替えない。
- Windowsアプリ非起動時の通知は、GAS単独やmanifest設置だけでは成立しない。Web Push・Service Worker・購読管理・Push配信元・ブラウザ/OSの制約を検証し、実装可能性を確定する。メール等の通知方式はユーザーと協議。
- 社内顧客情報・依頼内容・成果物・本人識別子をPublicリポジトリ、公開デモ用静的ファイル、URLパラメータに露出しない。

## 7. データモデル（論理設計のたたき台）

| エンティティ | 必要な主な情報 |
| --- | --- |
| requests | request_id、source_record_id、タイトル、依頼内容、顧客参照、営業本人参照、所属、担当SA、状態、作成・更新・完了日時 |
| messages | message_id、request_id、送信者参照、本文、送信日時、閲覧状態の管理キー |
| attachments | attachment_id、request_id、DriveファイルID、ファイル名、登録者、登録日時、返却対象フラグ |
| activity_log | event_id、request_id、操作者、操作種別、旧値・新値、日時 |
| notification_queue | notification_id、request_id、宛先参照、通知種別、送信状態、再試行情報（必要に応じて） |

列名・シート構成・IDの採番規則は未確定。保存処理には同時更新対策、二重送信防止、権限確認、監査ログを設ける設計とする。営業AIメモの既存シートを直接書き換える方針は採らない。

## 9. 決定待ちの事項

- SA依頼を既存営業AIメモからどう検知・取り込むか（元データの実態・即時性・既存コード変更の可否）。

- 独立Web画面とGASの安全な通信方式。
- SA用Windows通知と営業通知の手段、アプリ未起動時の要件と利用環境。
- 依頼ステータスの例外遷移、担当変更ルール、完了後の再開可否。
- データの保持期間、ファイル容量・アクセス制御、エラー時の運用。
- 本番ホスティング／公開方式と社内公開制限。
