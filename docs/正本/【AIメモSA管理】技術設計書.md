## 2. 基本アーキテクチャ

### 2.1 採用方針

| 層 | 技術候補 | 責務 |
| --- | --- | --- |
| 営業側依頼入口 | 既存営業AIメモ | 音声・テキストによるSA依頼の登録。既存アプリは原則非改修 |
| フロントエンド | HTML・CSS・JavaScript | SA向け3カラム画面、営業向けスマホ画面 |
| アプリケーション処理 | Google Apps Script | 認証・認可連携、依頼取得・編集、スレッド、ファイル、通知制御 |
| 構造化データ | Google Sheets | 依頼、メッセージ、担当、履歴、添付参照、通知記録 |
| ファイル | Google Drive | PDF等の成果物の保存と参照 |
| ソース・文書 | GitHub（SA-management） | 設計・実装・変更履歴。実顧客データと秘密情報は格納しない |

Firebaseなどの代替基盤への変更は承認を要する。

### 2.2 論理的なデータの流れ

```text
営業担当者
  └─ 営業AIメモ（既存の音声・テキスト入力）
       └─ 既存SA依頼レコード
            └─ [元record_idを軸にSA依頼だけ連携。権限付き原文参照と冪等再試行の実装を検証]
                 └─ AIメモSA管理（GAS処理候補）
                      ├─ Google Sheets：依頼・担当・履歴・会話・通知
                      ├─ Google Drive：成果物
                      ├─ SA画面（Windows、GAS内の画面）
                      ├─ 営業画面（スマホ、GAS内の画面）
                      └─ 営業へGoogle Chat Webhook通知（部屋への通知）／SAは起動中画面に新着表示（3秒ごとの問い合わせ）
```

既存営業AIメモの元データは原則読み取り、SA管理の状態やスレッドを元シートへ書き戻さない。業務データはサーバー側の認可を経て取得・更新する。

## 3. 境界・既存営業AIメモ連携

**現行の保存方式**：`sa_case`はGAS内部の一時分類であり、DB独立列ではない。永続的には`deal_records.deal_theme`の「SA依頼｜」および`original_text`に残る（Codex調査報告と提示された保存結果）。

連携工程で確認する項目：
1. 確認済みの`record_id`・`user_key`・`branch_name`・`created_at`・`deal_theme`・`original_text`と、利用者マスター・読取権限・取込対象期間の対応。
2. 営業AIの表は、既存GASを変更せず、Sheets API読み取り専用（`spreadsheets.readonly`）で参照する（`SpreadsheetApp.openById` は編集権限を要求するため使わない）。SA管理の表は `spreadsheets.currentonly`、添付は `drive.file` で扱う。元シートへの書き込みは行わない。
3. 同一`source_record_id`の再取り込み防止。取り込み失敗の記録、再実行時の冪等性、部分成功時の再処理。
4. 取込は5分ごとの定期実行。SAへは画面の3秒ごとの問い合わせ、営業へは質問・完了時のChat Webhook通知。
5. 所属営業所別の対象範囲と、登録済み依頼の変更・取消時の動作。

社員・営業所マスターは営業AIメモの既存マスターを直接参照する。参照権限とキーは工程00で確認済み。既存GASの公開デプロイ、ログイン設定、トークン処理、データ構造を無断変更しない。

### 3.1 現行実DB・GAS照合を踏まえたSA依頼連携（2026-10-20）

- 現行実DBの `deal_records` に `record_id`、`branch_name`、`user_key`、`deal_theme`、`original_text`、`deal_content` がある。独立した `sa_case`／`record_type` 列やSA専用5項目の列はない。
- Codexの現行GAS静的調査では、AIが一時分類 `sa_case` を使い、不足確認後に `deal_theme` を「SA依頼｜内容」として保存する。2026-10-20午前、ユーザー提示の実機履歴にも「SA依頼｜価格表作成」の保存がある。ローカルGASの直接確認やSA新システムの実通信検証は未実施。
- 新SA管理は初期導入の鹿児島営業所を対象に、信頼できる所属情報と `deal_theme` の「SA依頼｜」により依頼を選別する。`record_id` を元依頼IDとして重複取込を防ぐ。
- `deal_theme` と `original_text` を元のまま保持し、新SA管理側のAIで「誰に／何を／依頼の種類／決まっていること／いつまで」を構造化する。`deal_content` は必要に応じて補助参照する。不明な情報は推測補完しない。
- 既存営業AIメモの受付・確認・保存は原則変更せず、SA管理用DB・担当・会話・添付・通知は新システム側で扱う。旧「SA案件」の他拠点・過去データの移行は初期対象外。
- 確定（工程00、2026-10-28）：読取経路は営業AIの表のSheets API読み取り専用（`spreadsheets.readonly`）。所属識別は営業所名の文字列で判定する（利用者は `user_master.master_branch_name`、依頼は `deal_records.branch_name`。`branch_id` は営業所名）。
- 未検証（工程05で確認）：AI抽出精度、原文の完全性。

### 3.2 5項目AI構造化の技術境界

新SA管理側で元文章と5項目の抽出結果・抽出状態を別々に保持する。AIサービスはOpenAI APIを採用する。外部送信データ範囲・費用見積り・利用モデルと障害時の再処理は詳細設計対象であり、実データ送信・課金は別途明示承認を必要とする。既存営業AIメモには書き戻さない。

確定（工程00）：営業AIと同じ gpt-4o-mini、キーはスクリプトプロパティ AI_API_KEY、UrlFetchApp で呼ぶ。5項目はJSONスキーマで受け取り、返りの文字列「null」は取込時に null へ正規化する。4xx は再試行せず、429・5xx のみ待ち時間を倍にして最大3回再試行する。本物の依頼文の送信は1件ずつユーザー許可を得る。

## 4. 画面実装と境界

### 4.1 SA向けWindows画面

採用モックの左：依頼一覧／中央：詳細と進捗／右：会話・成果物を基準に実装する。受付・担当引受・担当変更・質問・回答確認・完了返却は同一画面で行えることを優先。サンプルデータ・疑似通知・疑似ファイルは本番処理ではなく、実装時に認可済みバックエンドにつなぐ。

### 4.2 営業向けスマートフォン画面

GAS内の営業用画面（`doGet` の `view` で切替）で、鹿児島のSA依頼全件の一覧・状態を閲覧し、自分の依頼で絞り込む。依頼ごとのスレッド、返信、完了結果、閲覧可能な成果物を扱う。営業AIメモ本体へ新しいスレッド機能を追加しない。

### 4.3 Web公開方法

SA画面・営業スマホ画面ともGASの中に置く（`HtmlService.createTemplateFromFile` ＋ `evaluate`、`google.script.run`、`doGet` の `view` で切替、`viewport` 指定）。営業AIと同じ作りとする。公開は「実行＝デプロイ者、アクセス＝組織内」。本番画面をGitHub Pagesに置かない。現在のGitHub Pagesは**モック公開先**であり、変更しない。Publicリポジトリ／公開静的サイトに顧客情報、SA依頼内容、業務APIの秘密、認証情報を置かない。

## 5. 認証・権限制御

### 5.1 必須の安全要件

- 実利用者を信頼できる仕組みで認証し、営業・SA・営業所を確定する。
- 営業は鹿児島のSA依頼全件を閲覧し、自分の依頼を絞り込める。投稿は原則本人依頼のみ。添付取得は別権限とし、操作ごとにサーバー側で認可する。SAは共通一覧を利用して引受・引継ぎでき、担当変更に管理者承認を要しない。
- 依頼IDやURLを推測・交換しても他者データを参照できない。
- **全API操作をサーバー側で認可**する。フロントの非表示・ロール切替はセキュリティではない。
- 既存利用者マスターのユーザー識別子、所属、ロールとの対応は現行正本・実装と照合する。

### 5.2 本人判定の方式

営業AIと同じ方式とする。`Session.getActiveUser().getEmail()` を営業AIの `user_master.user_key` と照合し（前後の空白・大文字小文字は無視）、`active_flag` が「有効」の利用者だけを許可する。SA＝`role` が `sales_support`、営業＝`sales`。マスターは複製せず直接参照する。GAS Webアプリの公開は「実行＝デプロイ者、アクセス＝組織内」とする。認証情報をURL、ローカルストレージ、Public GitHub、ソースに固定保存しない。

## 6. フロントエンドとGASの通信

画面はGASの中に置くため、別オリジンからの通信は行わない（CORS・プリフライト・外部ホストからの `fetch` は使わない）。画面からサーバー処理の呼び出しは `google.script.run` で行う。

GAS側の統一サービス層で本人・所属・権限を検証してから依頼・会話・ファイル操作へ振り分ける。入力値検証、重複送信対策（`client_operation_id`）、セッション失効時の処理を設ける。具体的な関数名・API仕様はAPI・内部関数設計書で定める。

## 7. データ保存・整合性

### 7.1 論理モデル（シート名は候補）

| 論理エンティティ | 情報 |
| --- | --- |
| 依頼 | 依頼ID、元レコードID、依頼者、営業所、担当SA、状態、本文、登録・更新・完了日時 |
| メッセージ | 会話ID、依頼ID、投稿者、本文、日時、既読に関する情報 |
| 添付ファイル | 添付ID、依頼ID、DriveファイルID、登録者、返却対象、登録日時 |
| 操作履歴 | 操作ID、依頼ID、操作者、操作、旧値・新値、日時 |
| 通知 | 通知ID、種別、対象依頼、宛先、配信状態、再試行状況 |
| 利用者・営業所 | 既存マスターと本アプリのアクセス範囲の対応 |

物理シート名、列順、必須値、ID採番・一意制約、参照関係はDB設計書で定義する。初期導入を鹿児島に限定してもデータモデルを鹿児島専用の固定値で実装しない。

### 7.2 更新の一貫性

- 依頼の二重取込を防ぐ（元記録ID等による冪等性）。
- 同時担当引受は排他制御や更新前提条件の照合を検討する。
- ステータス遷移はサーバーで検査。質問の保存ではカード進捗を変更しない。
- 営業の回答を保存後、SAへの新着・未読を整合的に更新する。
- 完了コメント・成果物参照・完了状態を矛盾なく登録し、送信失敗しても完了結果を喪失しない。
- 関連する操作履歴を追跡可能に残す。

Sheetsの同時処理対策としてGASのLockService等を検証候補にできるが、ロック範囲や性能は後続設計で確定する。

### 7.3 本人設定・期限・競合の保存処理

既存7シート構成を維持し、SA個人別表示順は`sa_read_cursors`の`user_id × request_id`に`sort_order`を保存する。本人の表示順のみ更新し、他SAの順序・依頼共通状態は変更しない。SA備考は`sa_requests.sa_note`へ、期限原文・解釈日・至急区分・訂正者・日時は同じ依頼に保存し、原文スナップショットは変更しない。

GAS `LockService`下で`row_version`の期待値を照合して更新競合を拒否する。投稿は`client_operation_id`で冪等化し、訂正は元投稿を残して同じ依頼スレッドに追記する。変更は監査履歴へ記録する。

## 8. ファイル保存・返却

- 営業所ごとに管理設定したGoogle Driveフォルダ（鹿児島は既存Drive配下）に成果物を置き、必要な成果物を格納する。保存成功時にファイルID・URLを取得し、当該依頼スレッドへリンクを記録する。添付なしでも完了可能。フォルダID・共有権限・命名・容量は実装前に確認する。
- 添付の参照情報を依頼データと関連付ける。ファイルIDの存在だけで権限があると判断しない。
- SAによるアップロード、完了時の返却対象選択、営業による取得を個別に認可する。
- Drive共有リンクを安易に「リンクを知っている全員」へ公開しない。ログ・通知本文にも必要以上の顧客情報を載せない。
- ドライブ操作が失敗した場合は完了操作を成功扱いしないなど、整合性・再試行ルールを設計する。

### 8.1 営業所別Driveフォルダの管理

SA管理GASのScript Propertiesで`SA_DRIVE_FOLDER_<branch_id>`に営業所別の既存DriveフォルダIDを保持する。既存の運用権限で設定し、独立設定画面・SA管理者ロール・マスター複製を設けない。ファイル登録時は所属とフォルダ権限を確認し、設定欠落・到達不能なら保存を拒否する。設定変更者・日時・営業所を運用記録に残す。設定・変更は管理者（ユーザー本人）がGASの設定画面（スクリプトプロパティ）で行い、`tasks/CHAT_CURRENT.md` に記録する。実フォルダID・アクセス権は別途許可された検証で確認する。

## 9. 通知設計

| イベント | 想定受信者 | 要件 | 配信方法 |
| --- | --- | --- | --- |
| 新規依頼登録 | 対象営業所のSA | 起動中の共通一覧に新着を表示 | 画面内通知（3秒ごとに `google.script.run` で問い合わせ） |
| 営業への質問投稿 | 依頼した営業 | 該当依頼を開き回答できる | Google Chat Webhook（営業AIと同じ部屋への通知。文面に依頼者名・依頼件名） |
| 営業からの回答 | 所属営業所のSA画面利用者 | 起動中の新着・未読表示。カード状態は自動変更しない | 画面内表示（3秒ごとに問い合わせ） |
| 完了・成果物返却 | 依頼した営業 | 結果と成果物の案内 | Google Chat Webhook（営業AIと同じ部屋への通知。文面に依頼者名・依頼件名） |
| 担当変更 | 関係するSA | 共有一覧と履歴から担当変更を確認 | 起動中の画面更新。閉アプリ通知なし |

SAの新着確認はSA管理画面を開いている間の画面内表示とする。閉画面・閉アプリのWeb Pushは初期要件に含めない。

SAが質問・完了した場合の営業向け通知手段は、営業AIと同じGoogle Chat Webhook（部屋への通知）とし、本人宛ての個別送信は行わない。SA担当者によるGmail手動送信を前提にしない。送信結果は `sa_notifications` に記録し、配送結果で依頼状態を変えない。**質問・返信・訂正・完了のやり取りの正本はSA管理の1依頼1スレッド**である。カード進捗はカード上の明示操作で更新し、スレッド投稿・Google Chat配送では自動変更しない。送信済み投稿の訂正は元投稿を残して追記する。再送・配信失敗、二重送信防止、リンク認可を設計する。**通知成功と業務データ保存成功は別状態として管理する。**

## 10. 端末互換性

- PWAは採用しない。GAS内の画面ではService Workerを登録できず、PWAとして成立しないことを工程00で確認した。閉画面・閉アプリ通知は行わない。
- スマホ向けの表示は、営業AIと同じ方式で `viewport`（`width=device-width, initial-scale=1, viewport-fit=cover`）を指定したGAS内の画面とする。
- オフライン対応は行わない。顧客データの端末キャッシュ保存を実装しない。
- 対象ブラウザ・会社のWindows管理ポリシーを確認する。
- 営業側のスマートフォンについて利用OS・ブラウザで画面とログインを実機確認する。

## 11. 公開・運用・障害対応

- 開発・検証・本番のデータと公開先を混同しない。
- GASの実行権限・公開範囲、Sheets/Drive権限、フロントの公開場所、通知サービスの資格情報を別途決定する。
- SA管理GASの必要権限：営業AIの表の読み取りは `spreadsheets.readonly`（Sheets API）、SA管理の表は `spreadsheets.currentonly`、添付は `drive.file`、外部通信（OpenAI・Chat）は `script.external_request`、本人判定は `userinfo.email`。営業AIの表やファイルを書き換えられる権限（`spreadsheets`、`drive`）は使わない。
- 秘密情報はGitHubや公開フロントへ保存しない。ログにトークン・個人情報を不要に出力しない。
- 取り込み失敗、通知失敗、送信競合、Drive保存失敗について運用担当が確認・再実行できるようにする。
- 監査記録、バックアップ、退職・異動時のアクセス停止、障害時の復旧を後続設計に含める。
- `main`への変更、PR・マージ、GAS反映、公開更新は工程ごとの承認範囲に従う。モックの公開URLを維持し、既存営業AIメモの本番環境に無断操作しない。

## 12. 技術検証の優先順位と合否

| ID | 検証 | 合格のための証拠 |
| --- | --- | --- |
| TV-01 | SA依頼の元データ確認 | 現行コード・データ列・ユーザー・営業所の参照関係とサンプル動作を照合 |
| TV-02 | 認証と所属・ロール | 許可・未許可の両方でサーバー側の認可判定を確認 |
| TV-03 | 別オリジンとGASの接続 | GAS内画面で確認済み（工程00）。別オリジン通信は行わない |
| TV-04 | 依頼の二重取込・同時引受 | 同時更新や再試行でも二重化・上書き事故がない |

`静的確認`、`隔離モック`、`実通信`、`実機確認`を区別し、いずれも未実施なら未実施と記録する。実機が必要なものは検証が終わるまで合格としない。

### 12.1 依頼連携と状態更新の方針

- `record_id` 連携は工程00で確認済み。SA依頼として識別された行を `record_id` を鍵に取り込み、非SA商談を業務DBに取り込まない。
- スレッドへの質問・回答・訂正はカードの進捗を変更しない。営業回答待ち・対応中等の切替はカード上の明示操作で行い、完了後も再開できる。
- AI候補、顧客情報の送信範囲、費用は別途提示・承認されるまで外部通信や課金を行わない。
