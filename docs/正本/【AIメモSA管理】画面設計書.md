状態：初稿・確認中。位置づけ：実装用画面設計初稿。採用済みモックと全5正本を踏まえ、画面の入力・表示・操作・権限・状態を整理する。

## 1. 根拠と設計境界
参照：概要企画書、要件定義書、技術設計書、DB設計書、API・内部関数設計書（いずれもGitHub `main` のdocs/正本）、docs/計画/【AIメモSA管理】未確定事項確認書.md、ルールブック、GitHubリポジトリ標準規約、CHAT_CURRENT、TASK_CURRENT。
採用モックのindex.html / app.js / styles.css / design-qa.mdも確認した。

- 共通営業AIメモの音声・テキスト受付は原則改修しない。SA管理は既存deal_recordsの鹿児島の「SA依頼｜」を取り込み、新管理側のAIで5項目に構造化する。
- SA向けWindows画面は既存モックの「左サイドバー＋上部KPI＋3カラム」を採用。モックはサンプルデータで、本番の認証・通知・保存とは区別する。
- 営業向けはSA画面内の「営業役」デモ切替ではなく、**本人用の独立したスマホ対応画面**を設計する。
- 4状態：未担当／対応中／営業回答待ち／完了。新着・未読は状態とは別情報。
- 画面非表示だけに頼らず、全操作でサーバー側の本人・営業所・役割認可を行う。

## 3. SA-01 ワークスペース：レイアウトと項目

### 3.1 共通ヘッダー／左サイドバー／KPI
- ヘッダー：システム名、依頼検索、未読・新着、通知アイコン、認証済み利用者名・所属。
- サイドバー：採用済みモックはダッシュボード、SA依頼一覧、未担当、対応中、営業回答待ち、完了、担当別、設定を表示する。独立したダッシュボード・担当別・設定機能は確定要件ではなく、実装範囲を追加判断する。
- KPI：新着・未読／未担当／対応中／営業回答待ち／完了の件数。数値は認可済み鹿児島対象レコードから算出。クリック時は対象一覧に絞り込む。
- モック内の件数固定値、利用者固定名、サンプル環境の表示は本番では用いない。ダッシュボード等の独立機能をモックのナビラベルだけから実装済みとは扱わない。

### 3.2 左カラム：依頼一覧
| 表示／入力項目 | 内容 | 動作 |
| --- | --- | --- |
| ステータス | 4状態の絞込 | 選択条件で一覧更新 |
| 担当者 | SA担当者／未担当 | 認可済み担当者から選択 |
| 期限 | 本日・期限超過・3日以内等 | 正規化可能な期限に基づく。AI不明値は誤分類しない |
| キーワード | 件名・依頼者・得意先等の検索 | 表示可能なデータ範囲のみ |
| 要対応優先 | 未読・期限等の重要度 | 並び順。状態変更はしない |
| 依頼カード | タイトル、状態、営業名、得意先名、担当SA、期限、未読件数 | 選択時に中央・右を連動 |
| 件数・クリア | 絞込結果件数・条件初期化 | 条件変更時に再計算 |

初回読込中、0件、通信失敗、取込構造化待ちを区別して表示する。別営業所・他権限の記録は一覧に渡さない。

### 3.3 中央カラム：依頼詳細・担当・進捗・履歴
- ヘッダー：依頼件名、4状態、依頼日時、営業担当者、営業所。
- 基本情報：得意先（元レコードにある場合のみ）、元依頼内容／原文、AI抽出5項目「誰に」「何を」「依頼の種類」「決まっていること」「いつまで」。
- AI構造化が不十分な場合は「未確認」等と原文を表示し、空欄を架空値で補完しない。元件名とAI構造化結果を区別する。
- 担当者名（未担当を許容）、担当する、担当変更、営業へ質問、対応再開、完了登録、対応結果・履歴確認。
- 履歴：操作日時、操作者、操作種別、変更内容。依頼ごとの履歴を時系列に表示。

| 現状態 | 許可する主操作 | 操作後の状態 |
| --- | --- | --- |
| 未担当 | 担当する | 引受成功後に対応中 |
| 対応中 | 営業へ質問・担当変更・完了登録 | 質問の**保存成功後**に営業回答待ち／完了確定後に完了 |
| 営業回答待ち | 回答確認・対応再開・担当変更 | 対応再開の成功後に対応中 |
| 完了 | 結果・成果物・履歴閲覧 | 通常は閲覧。再開ルールは要決定 |

担当引受・担当変更時は最新状態・担当・更新バージョンを再検査。競合時は上書きせずエラーを表示して再読込を促す。操作権限外のボタンは表示しないが、API側でも拒否する。

### 3.4 右カラム：会話・成果物・完了コメント
- スレッド：投稿者、SA／営業の区分、投稿日時、本文、未読表示。投稿フォーム、送信ボタン。送信中・成功・失敗・再送可能を区別する。
- SAの「営業へ質問」は入力を促すだけで状態を変えない。**実際に質問投稿が保存された時点**で営業回答待ちに更新し、通知対象を記録する。
- 添付：PDF等の名称、サイズ、登録日時、登録者、返却対象。ファイル選択とアップロード結果、プレビュー・取消／差替えは認可済み操作で処理。
- 備考欄はモック由来で保存仕様・本番採用は未決。完了コメントと返却対象資料選択は要件に基づく。
- PDFなしで完了確認画面を開けるのはモックで確認した挙動。本番の完了条件として添付を必須にするかは未決（SA-U-09）。無条件に許可・禁止する仕様は決めない。

## 4. SA-02 担当引受・担当変更
1. 依頼ID、現在担当、候補SA、現在の状態を表示。
2. 引受は「未担当」のときだけ成功。担当変更では変更先を選択し確定する（変更承認要否は業務未決事項）。
3. サーバーが所属・権限・最新バージョンを検査し、変更と履歴追記に成功したら詳細・一覧・KPIを更新。
4. 競合・許可外・保存失敗では状態を更新したように見せない。

## 5. SA-03 完了・営業への返却確認
- 表示：依頼件名、営業担当者、完了コメント、返却対象成果物、PDFなしの有無。
- 実行：内容確認→完了確定→完了時刻と操作履歴保存→営業宛の通知対象を作成。通知が失敗しても本体の保存結果は維持し、通知だけ再試行可能とする。
- 保存に失敗したら完了表示しない。二重クリック防止・処理中表示を設ける。
- 完了後の再開・成果物差替えは未決事項確認書U-07/U-09に従って確定する。

## 6. SA-04 新着／未読・通知
- 新規SA依頼、営業からの回答等の通知候補を日時・種別・対象依頼名で表示。期限注意はモック由来であり、通知条件の採用は未決（SA-U-05）。クリックすると認可確認後に該当依頼を開く。
- アプリ内の未読と4状態を混同しない。既読とする時点はデータ設計に合わせる。
- アプリを閉じたWindowsへの通知は、画面表示そのものでは実現できない。配信技術・社内PC条件・費用を別途確定する。モックの疑似通知を本番扱いしない。

## 7. SL-01 営業本人のスマホ依頼一覧（新規実装）
- 認証済み営業本人が発したSA依頼のみ表示。他営業の案件・SA全体一覧は見せない。
- 表示：依頼タイトル、受付日時、進捗、担当SA（表示可の範囲）、期限、SAからの未読質問、完了通知。状態・未読で絞込可能とする。
- 依頼を選ぶとSL-02へ遷移。URLで他人の依頼IDを渡されても認可エラーとする。
- SA依頼の新規入力フォームは設けず、入力入口は既存営業AIメモに維持する。

## 8. SL-02 営業本人の詳細・返信・成果物
- 表示：元依頼タイトル、元入力原文、構造化済み依頼内容、進捗、担当SA、営業への質問、会話履歴、完了コメント、返却対象ファイル。
- 質問への返信：本文入力→送信→保存結果反映。空欄不可・二重送信防止・失敗時の再試行表示。営業からの返信が保存されてもSAの「対応中」への自動復帰は暫定で行わず、SAの確認・再開操作を前提とする設計案（運用判断待ち）。
- 添付閲覧：本人認可後に閲覧・取得を許可。Driveのリンクが分かるだけで他人が閲覧できる構成にしない。
- 完了時：返却内容と成果物を確認する。SA担当変更・進捗編集・他人への投稿は不可。

## 9. CM-01 認証・状態・エラー表示
| 状況 | 表示と操作 | 保存処理 |
| --- | --- | --- |
| 認証未完了・期限切れ | 本人確認が必要と示し再認証導線を案内 | データ表示・更新しない |
| 権限なし／他営業所 | 対象を表示できない旨を通知 | 対象本文・ファイルを返さない |
| データ読込中／0件 | 読込中・該当なしを区別 | 誤って完了扱いしない |
| 通信失敗 | 再取得ボタンと短い説明 | 既存画面の状態を勝手に成功へ変更しない |
| 担当競合・状態競合 | 最新情報を再読込するよう案内 | 上書きしない |
| 取込済み・AI構造化未完了 | 原文を表示し構造化状態を区別 | 原文を失わず再処理可能にする |
| 投稿・添付・完了失敗 | 対象操作の失敗を明示 | 失敗した操作だけ再試行。二重登録防止 |
| 通知失敗 | 記録の保存とは別に配送失敗を表示 | 保存済み本文・完了状態は維持 |

## 11. 画面受入の必須シナリオ
1. 鹿児島のSA依頼が一覧へ重複なく表示され、原文とAI構造化5項目を確認できる。
2. 未担当の依頼を1人のSAだけが引き受け、他のSAの同時引受は競合扱い。
3. SAが質問を作成しただけでは状態が変わらず、投稿保存後に営業回答待ちとなる。
4. 営業本人がスマホから質問に返信でき、SA側に新着・未読が反映される。
5. SAが引継ぎしても依頼原文・会話・資料・履歴が残る。
6. PDFあり・なしの双方で完了確認と返却が整合し、営業本人が結果を取得できる。
7. 別営業・別営業所・未認証の閲覧・操作をサーバー側が拒否する。
8. 入力・通信・通知・添付失敗時に成功と誤表示せず、二重送信を防止する。
9. SAのWindows画面と営業スマホ画面を、それぞれ利用者目線で確認する。

## 2026-10-23 業務方針の確定・設計適用（SA-U-01〜22）

2026-10-23の利用者判断を反映する。本文に残る古い未決表現・候補は、本節と `docs/計画/【AIメモSA管理】未確定事項確認書.md` §3.2 の最新判断に従って設計時に整合修正する。既存の履歴や技術検証待ち事項を消去しない。

- SA管理画面を開いているときに新着依頼・営業返信が分かればよく、閉アプリ通知・Web Pushは初期要件外。営業向けは、SAからの質問・完了をGoogle Chatで個別通知するが、**会話・回答・進捗の主体はSA管理の依頼スレッド**とする。
- **1依頼1スレッド**でメッセージ、訂正の追加投稿、完了コメント、必要に応じたDrive成果物リンクを保持。送信済み投稿は上書き削除せず訂正投稿を追加する。
- **状態遷移はGoogle Chatの送信を契機にせず、スレッド上の業務操作の保存成功を契機とする。** SAの質問が保存されれば営業回答待ちへ移す。営業返信が保存された場合の対応中への復帰条件は設計側で決めて検証する。通常投稿・訂正投稿で誤遷移させない。配送失敗で保存済みの状態を戻さない。
- SAは全員で共通の依頼を閲覧・引受・引継ぎ可能で担当変更に管理者承認は不要。営業担当者は全依頼を閲覧でき、自分の依頼で絞り込める。書込・添付参照の認可は設計側が別途安全に確定する。利用者は管理責任者。
- 鹿児島営業所の**既存Drive配下**を成果物保存先として使い、登録ファイルのリンクを自動取得して同じスレッドに表示。ファイルがない依頼（サンプル出荷など）も完了可能。SA一覧の優先順は手動で変更できる構成。
- 連携は営業AIメモから**SA依頼だけのIDをリンクする案を優先検証**。非SA商談を新SA業務DBへ混入させず、元record_idで重複防止する。実際の連携・反映速度は未試験であり、方式は検証後に設計確定。
- AIの製品・外部送信対象データ・費用は設計側が比較し提示するまで**未承認**。外部送信や課金をこの業務方針決定によって許可したとはみなさない。
- その他SA-U-01〜22の提示推奨方針は、**SA-U-16の上記修正とSA-U-20の条件付き判断を除き了承**された。設計側で詳細設計・整合修正・工程表・実装指示書を作成する。仕様了承と実装完了を混同しない。
