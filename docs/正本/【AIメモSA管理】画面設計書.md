# 【AIメモSA管理】画面設計書

作成日：2026-10-20  
対象：鹿児島営業所から初期導入する「AIメモSA管理」  
状態：確定済み業務方針を反映した画面設計。実装・実通信・実機確認は未完了。採用モックと他5正本を照合し、全6正本で画面の入力・表示・操作・権限・状態を整理する。

## 1. 根拠と設計境界
参照：概要企画書、要件定義書、技術設計書、DB設計書、API・内部関数設計書（いずれもGitHub `main` のdocs/正本）、docs/計画/【AIメモSA管理】未確定事項確認書.md、ルールブック、GitHubリポジトリ標準規約、CHAT_CURRENT、TASK_CURRENT。
採用モックのindex.html / app.js / styles.css / design-qa.mdも確認した。

- 共通営業AIメモの音声・テキスト受付は原則改修しない。SA管理は既存deal_recordsの鹿児島の「SA依頼｜」を取り込み、新管理側のAIで5項目に構造化する。
- SA向けWindows画面は既存モックの「左サイドバー＋上部KPI＋3カラム」を採用。モックはサンプルデータで、本番の認証・通知・保存とは区別する。
- 営業向けはSA画面内の「営業役」デモ切替ではなく、**本人用の独立したスマホ対応画面**を設計する。
- 4状態：未担当／対応中／営業回答待ち／完了。新着・未読は状態とは別情報。
- 画面非表示だけに頼らず、全操作でサーバー側の本人・営業所・役割認可を行う。

| ID | 画面／表示単位 | 利用者 | 開き方 |
| --- | --- | --- | --- |

| SL-01 | 所属営業所のSA依頼一覧（本人依頼絞込可） | 導入営業所の営業 | 営業専用スマホ入口／通知リンク |
| SL-02 | 営業向け依頼詳細・本人依頼への回答・認可済み成果物 | 導入営業所の営業 | SL-01の依頼選択／認証済み通知リンク |

SA側の3カラムは同一画面内の連動表示とする。依頼選択により中央・右を同期し、別依頼の本文・メッセージを混在させない。

## 3. SA-01 ワークスペース：レイアウトと項目

### 3.1 共通ヘッダー／左サイドバー／KPI
- ヘッダー：システム名、依頼検索、未読・新着、通知アイコン、認証済み利用者名・所属。
- サイドバー：採用済みモックはダッシュボード、SA依頼一覧、未担当、対応中、営業回答待ち、完了、担当別、設定を表示する。独立画面を新設しない。担当別は一覧の担当者選択、設定は営業所ごとの設定値、ダッシュボードは既存KPIで扱う。
- KPI：新着・未読／未担当／対応中／営業回答待ち／完了の件数。数値は認可済み所属営業所の対象レコードから算出。クリック時は対象一覧に絞り込む。
- モック内の件数固定値、利用者固定名、サンプル環境の表示は本番では用いない。ダッシュボード等の独立機能をモックのナビラベルだけから実装済みとは扱わない。

### 3.2 左カラム：依頼一覧
| 表示／入力項目 | 内容 | 動作 |
| --- | --- | --- |
| ステータス | 4状態の絞込 | 選択条件で一覧更新 |
| 担当者 | SA担当者／未担当 | 認可済み担当者から選択 |
| 期限 | 本日・期限超過・3日以内等 | 正規化可能な期限に基づく。AI不明値は誤分類しない |
| キーワード | 件名・依頼者・得意先等の検索 | 表示可能なデータ範囲のみ |
| 要対応優先 | 未読・期限等の重要度 | 自動優先表示。本人別手動並べ替えとは区別し、状態変更なし |
| 手動並べ替え | SA本人が依頼カードの表示順を変更 | API-14で本人の表示順だけ保存・次回復元。他SAの順序や共通状態は不変 |
| 期限訂正 | 元の期限表現・解釈日・至急区分を確認して訂正 | API-15で元原文を保持し訂正内容を保存。一覧と期限絞込を更新 |
| 依頼カード | タイトル、状態、営業名、得意先名、担当SA、期限、未読件数 | 選択時に中央・右を連動 |
| 件数・クリア | 絞込結果件数・条件初期化 | 条件変更時に再計算 |

初回読込中、0件、通信失敗、取込構造化待ちを区別して表示する。別営業所・他権限の記録は一覧に渡さない。

### 3.3 中央カラム：依頼詳細・担当・進捗・履歴
- ヘッダー：依頼件名、4状態、依頼日時、営業担当者、営業所。
- 基本情報：得意先（元レコードにある場合のみ）、元依頼内容／原文、AI抽出5項目「誰に」「何を」「依頼の種類」「決まっていること」「いつまで」。
- AI構造化が不十分な場合は「未確認」等と原文を表示し、空欄を架空値で補完しない。元件名とAI構造化結果を区別する。
- 担当者名（未担当を許容）、担当する、担当変更、営業へ質問、対応再開、完了登録、対応結果・履歴確認。
- 履歴：操作日時、操作者、操作種別、変更内容。依頼ごとの履歴を時系列に表示。

| 現状態 | 許可する主操作 | 操作後の状態 |
| --- | --- | --- |
| 未担当 | 担当する | 引受成功後に対応中 |
| 対応中 | 営業へ質問・担当変更・完了登録 | 質問の投稿では状態不変。カード上の進捗操作で変更／完了登録で完了 |
| 営業回答待ち | 回答確認・対応再開・担当変更・完了登録 | 対応再開成功で対応中。完了登録成功で完了 |
| 完了 | 結果・成果物・履歴閲覧・進捗再変更 | カード上で対応中等へ戻せる |

担当引受・担当変更時は最新状態・担当・更新バージョンを再検査。競合時は上書きせずエラーを表示して再読込を促す。操作権限外のボタンは表示しないが、API側でも拒否する。

### 3.4 右カラム：会話・成果物・完了コメント
- スレッド：投稿者、SA／営業の区分、投稿日時、本文、未読表示。投稿フォーム、送信ボタン。送信中・成功・失敗・再送可能を区別する。
- SAの「営業へ質問」は入力を促すだけで状態を変えない。質問投稿はスレッドに保存し通知対象を記録する。カードの進捗を自動変更しない。
- 添付：PDF等の名称、サイズ、登録日時、登録者、返却対象。ファイル選択とアップロード結果、プレビュー・取消／差替えは認可済み操作で処理。
- 備考欄は完了コメントとは別にAPI-13で保存・更新し、詳細再表示時に読み戻す。完了コメントと返却対象資料選択は要件に基づく。
- 添付が0件でも完了確認・完了登録ができる。完了コメントを記録し、資料がある場合だけ返却対象を確認する。

## 4. SA-02 担当引受・担当変更
1. 依頼ID、現在担当、候補SA、現在の状態を表示。
2. 引受は「未担当」のときだけ成功。担当変更では変更先を選択し確定する（SA同士の担当変更に管理者承認は不要）。
3. サーバーが所属・権限・最新バージョンを検査し、変更と履歴追記に成功したら詳細・一覧・KPIを更新。
4. 競合・許可外・保存失敗では状態を更新したように見せない。

## 5. SA-03 完了・営業への返却確認
- 表示：依頼件名、営業担当者、完了コメント、返却対象成果物、PDFなしの有無。
- 実行：内容確認→完了確定→完了時刻と操作履歴保存→営業宛の通知対象を作成。通知が失敗しても本体の保存結果は維持し、通知だけ再試行可能とする。
- 保存に失敗したら完了表示しない。二重クリック防止・処理中表示を設ける。
- 完了から対応中等へ戻れる。完了はロックではない。

## 6. SA-04 新着／未読・通知
- 新規SA依頼、営業からの回答等の通知候補を日時・種別・対象依頼名で表示。期限接近は一覧で注意表示し、自動通知しない。クリックすると認可確認後に該当依頼を開く。
- アプリ内の未読と4状態を混同しない。既読とする時点はデータ設計に合わせる。
- SA新着通知は管理画面を開いている間に表示する。閉画面・閉アプリ通知は初期要件外。モックの疑似通知を本番扱いしない。

## 7. SL-01 所属営業所のSA依頼一覧（新規実装）
- 認証済み営業は導入営業所の全SA依頼を閲覧でき、本人の依頼だけに絞り込める。投稿は原則本人の依頼に限る。
- 表示：依頼タイトル、受付日時、進捗、担当SA（表示可の範囲）、期限、SAからの未読質問、完了通知。状態・未読で絞込可能とする。
- 依頼を選ぶとSL-02へ遷移。URLで別営業所の依頼IDを渡された場合は認可エラーとする。同じ営業所の他者依頼は閲覧できるが投稿は原則本人依頼に限定する。
- SA依頼の新規入力フォームは設けず、入力入口は既存営業AIメモに維持する。

## 8. SL-02 営業向け詳細・本人依頼の返信・認可済み成果物
- 表示：所属営業所の依頼タイトル、元入力原文、構造化済み依頼内容、進捗、担当SA、会話履歴、完了コメント。成果物はファイル別認可を通ったものだけ閲覧・取得可能。
- 質問への返信：本人の依頼に対して本文入力→送信→保存結果反映。空欄不可・二重送信防止・失敗時の再試行表示。返信の保存ではカードの状態を変更しない。SAがカード側の明示操作で対応中に戻す。
- 添付閲覧：自分の依頼の返却対象ファイルは本人認可後に取得可能。他者の依頼本文が見えても他者の成果物は認可なしで取得できない。Driveのリンクが分かるだけで他人が閲覧できる構成にしない。
- 完了時：返却内容と成果物を確認する。SA担当変更・進捗編集・他人への投稿は不可。

## 9. CM-01 認証・状態・エラー表示
| 状況 | 表示と操作 | 保存処理 |
| --- | --- | --- |
| 認証未完了・期限切れ | 本人確認が必要と示し再認証導線を案内 | データ表示・更新しない |
| 権限なし／他営業所 | 対象を表示できない旨を通知 | 対象本文・ファイルを返さない |
| データ読込中／0件 | 読込中・該当なしを区別 | 誤って完了扱いしない |
| 通信失敗 | 再取得ボタンと短い説明 | 既存画面の状態を勝手に成功へ変更しない |
| 担当競合・状態競合 | 最新情報を再読込するよう案内 | 上書きしない |
| 取込済み・AI構造化未完了 | 原文を表示し構造化状態を区別 | 原文を失わず再処理可能にする |
| 投稿・添付・完了失敗 | 対象操作の失敗を明示 | 失敗した操作だけ再試行。二重登録防止 |
| 通知失敗 | 記録の保存とは別に配送失敗を表示 | 保存済み本文・完了状態は維持 |

## 10. APIとの画面対応
| 画面操作 | 論理API（案） |
| --- | --- |
| 本人・役割の確定 | API-01 getMyProfile |
| 一覧・検索・絞込 | API-02 listRequests |
| 詳細・スレッド・ファイルの読込 | API-03 getRequestDetail |
| 担当する | API-04 claimRequest |
| 担当変更 | API-05 reassignRequest |
| 進捗・対応再開（完了登録は除く） | API-06 changeRequestStatus |
| 質問・回答投稿 | API-07 postMessage |
| 既読更新 | API-08 markThreadRead |
| 添付登録 | API-09 `registerAttachment` |
| 添付参照 | API-10 `getAttachmentAccess` |
| 完了返却（唯一の完了登録経路） | API-11 `completeRequest` |
| SA備考の編集・保存 | API-13 `updateSaNote` |
| 本人別手動並び順の保存 | API-14 `saveMyRequestOrder` |
| 期限の訂正 | API-15 `correctRequestDueDate` |
| 操作履歴参照 | API-12 `getActivityHistory` |

画面はサーバーが認可済みの結果のみ利用する。API名称・入力・返却・エラーコードはAPI設計の正本を優先する。

## 11. 画面受入の必須シナリオ
1. 鹿児島のSA依頼が一覧へ重複なく表示され、原文とAI構造化5項目を確認できる。
2. 未担当の依頼を1人のSAだけが引き受け、他のSAの同時引受は競合扱い。
3. SAが質問を作成・投稿してもカード進捗は変わらない。カード操作とスレッド投稿は独立。
4. 営業本人がスマホから質問に返信でき、SA側に新着・未読が反映される。
5. SAが引継ぎしても依頼原文・会話・資料・履歴が残る。
6. PDFあり・なしの双方で完了確認と返却が整合し、営業本人が結果を取得できる。
7. 営業は所属営業所の全依頼を閲覧できるが、投稿は原則本人依頼のみ。他営業所・未認証の閲覧・操作はサーバー側で拒否し、添付は別途認可する。
8. 入力・通信・通知・添付失敗時に成功と誤表示せず、二重送信を防止する。
9. SAのWindows画面と営業スマホ画面を、それぞれ利用者目線で確認する。
10. SA本人のカード並び順をAPI-14で保存・再表示し、別SAの順序・共通ステータスが変わらない。
11. 備考をAPI-13で保存・再表示し、完了コメントと混同しない。期限をAPI-15で訂正して原文保持・一覧更新を確認する。
12. 営業回答待ちから完了登録でき、通常進捗API-06で完了状態を直接登録できない。完了後の明示操作による再開を確認する。
13. 営業所ごとのDrive保存先設定に従いファイルが格納され、未設定・権限外では保存しない。

## 12. 未決事項と実装境界
- 認証、通信・ホスト、添付容量などの技術的な実装と検証は後続工程で扱う。閉アプリ通知、独自保存期限、完了後再開の可否、投稿訂正の方針など確定済みの業務判断を再質問しない。
- モックの「営業役」トグル、仮データ・固定KPI、Toastでの疑似保存、ローカルのみのPDF登録等は**試作用**。本番では本人認証とAPI結果に置き換える。
- 今回の作業は本画面設計書の作成。既存モック・他正本・GAS・DB・公開設定の改修は含めない。
