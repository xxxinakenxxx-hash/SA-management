# 【AIメモSA管理】API・内部関数設計書

作成日：2026-10-20  
文書状態：初稿・承認前（API実装・実通信未実施）  
初期導入：鹿児島営業所、将来の複数営業所利用を想定

## 1. 目的・参照関係

要件定義書FR-01〜20、NFR-01〜12、技術設計書、**同一ブランチの「【AIメモSA管理】DB設計書.md」**を基に、SA依頼の取込・表示・担当・会話・成果物・通知処理のAPI境界と内部関数候補を整理する。いずれも現時点では未承認の案である。関数名・アクション名・パラメータは設計候補であり、現行GASに存在することを意味しない。

Google Apps Scriptとの呼び出し形態（`google.script.run`、`doPost`など）、別オリジン通信の可否、認証方式、公開URLは**未確定**。特定方式を実装確定として扱わない。

## 2. 共通処理契約

- 全ての要求でサーバー側が利用者を認証し、所属・役割・対象依頼への権限を検査する。クライアント指定の`user_id`や`branch_id`を本人認証の根拠にしない。
- 読取も更新も営業本人または許可済みSAの範囲のみ。未認可の場合は対象の存在や顧客情報を漏らさない。
- 登録・変更処理は入力値を検証し、失敗時に「成功」と返さない。二重投稿防止の`client_operation_id`や`row_version`は**採用候補**。
- `request_id`は本システム内の不変ID、`source_record_id`は既存AIメモ元データのID。混同しない。
- 通知は業務更新の結果を起点に生成し、業務更新と配送成功を同一結果とみなさない。
- 日時・タイムゾーン、ページング、例外コード、入力長の制限は後続で確定する。

### 2.1 共通レスポンス案（未確定）

```json
{
  "success": true,
  "data": {},
  "error": null,
  "requestId": "operation-correlation-id"
}
```

失敗時は`success:false`、`error.code`と利用者向けメッセージを返す。個人情報、内部スタック、秘密情報を外部レスポンスに出さない。通信層のHTTPコード等は使用方式が決まってから定義する。

### 2.2 エラー種別案

| コード案 | 意味 | 対応 |
| --- | --- | --- |
| `AUTH_REQUIRED` | 本人確認不可 | 再認証導線、対象情報を返さない |
| `FORBIDDEN` | 操作権限なし | 対象データを返さない |
| `NOT_FOUND` | 依頼・添付なし | 経緯を漏らさず通知 |
| `VALIDATION_ERROR` | 入力不正 | 項目別に表示 |
| `CONFLICT` | 他者が状態等を変更 | 再取得して確認 |
| `DUPLICATE` | 元IDや投稿が登録済み | 冪等な同結果を返すか仕様確定 |
| `STORAGE_ERROR` | Sheets/Drive処理失敗 | 成功扱いせず記録 |
| `NOTIFICATION_ERROR` | 通知配送失敗 | 配信再試行対象として記録 |

エラーコード文字列も暫定案。

## 5. 主要処理フロー

### 5.1 元依頼の取込（FR-01/02）

1. 信頼できる内部処理として元記録を読み込む（`sa_case`とタイトル形式の実装を先に照合）。
2. 元IDと営業所・依頼者を検証。認可・所属情報が不足した元データを勝手に補完しない。
3. 同じ元IDの既存登録を調べ、重複の場合は新規レコードと新規通知を作成しない。
4. 新規のみ`sa_requests`へ「未担当」として登録、取込・操作ログ、SA宛通知対象を記録。
5. 途中失敗時は失敗位置と再試行可否を記録。元AIメモのデータを変更しない。

### 5.2 SA引受・引継ぎ（FR-06/07）

1. 呼出SAの所属と権限を検査。
2. 依頼の最新状態と担当、更新前提条件を確認。
3. 競合なく引受または担当変更を行い、履歴追記。
4. 競合した場合は`CONFLICT`を返し、他人の変更を上書きしない。SA担当変更の追加承認要否は未決定。

### 5.3 SA質問・営業回答（FR-09/10）

1. 依頼と投稿者のアクセス権を検査。
2. 投稿本文を検証、二重送信を防止。
3. メッセージを保存・履歴を記録。
4. SAから営業への**質問投稿が保存成功したときだけ**「営業回答待ち」に移す。
5. 必要な受信者へ通知キューを作成。
6. 営業返信時はSAへ通知。返信時の自動「対応中」復帰は未確定、独断で実装しない。
7. 通知配送失敗を投稿失敗と混同しない。

### 5.4 成果物・完了（FR-12/13）

1. SA本人と依頼の更新権限を検査。
2. ファイルの検証とDrive保存を行い、成功したファイル参照だけを`sa_attachments`へ記録。
3. 完了時、完了コメント・返却対象添付の存在と権限を確認。
4. 依頼を「完了」へ更新して履歴追記、営業宛通知キュー登録。
5. 添付保存／依頼更新／通知に不整合が生じた場合は誤って完了扱いしないよう、復旧手段を定義する。

## 6. 設計上の権限マトリクス案

| 操作 | 営業（本人依頼） | SA（許可所属） | 他営業・他所属 |
| --- | --- | --- | --- |
| 依頼一覧・詳細 | 自分の依頼のみ | 担当外を含め所属内対象 | 不可 |
| 担当引受・変更 | 不可 | 可（運用詳細未定） | 不可 |
| 状態変更・完了 | 不可 | 可（許可遷移のみ） | 不可 |
| メッセージ投稿 | 自分の依頼に回答・投稿 | 所属内の依頼へ投稿 | 不可 |
| 添付登録 | 初期対象外 | 可 | 不可 |
| 添付参照 | 自分へ返却されたもの | 所属内で許可されたもの | 不可 |
| 操作履歴 | 開示範囲未確定 | 許可された依頼の必要項目 | 不可 |
| 通知キュー直接操作 | 不可 | 不可（内部処理） | 不可 |

本人・SAを識別できない場合、一覧・詳細・添付・更新は拒否する。管理者ロールは要否未確定のため、現段階で全件参照権限を自動付与しない。

## 7. DB対応と更新規則

- `sa_requests`：API-02〜07/11、FN-02/05〜07。担当・進捗は最新行の更新前提条件を検査。
- `sa_messages`：API-03/07、FN-08。原則追加、既存発言を削除・差替えしない。
- `sa_attachments`：API-09/10/11、FN-10。DriveファイルIDは公開無認証URLではない。
- `sa_activity_log`：API-12、FN-09。監査ログの追記が必要。
- `sa_notifications`：FN-11/12。送信状態は依頼状態と別管理。
- `sa_read_cursors`：API-08、FN-13（候補）。
- `sa_import_log`：FN-14（候補）。

DB側の状態コード候補：`unassigned`→`in_progress`→`waiting_sales`→`in_progress`→`completed`。回答後の復帰操作、完了後の再開、例外遷移は未決定。公開画面で勝手な状態コードを受け付けない。

## 8. 非機能・安全設計

- **認証**：GAS Webアプリの実行主体とログイン利用者識別の成立を確認。画面から渡すメール文字列だけで本人確定しない。
- **通信**：独立Web画面→GASのCORS・リダイレクト・セッション挙動を実通信で検証。`google.script.run`の利用可否は画面ホスト構成に依存する。
- **CSRF等**：公開方式に応じ、セッション不正利用・不正操作・再送対策を設計。
- **排他**：Sheetsに対する同時引受・投稿・状態更新の競合を防ぐ。ロック方式と順序を検証。
- **添付**：形式・容量、Drive共有、ダウンロード導線は承認・実機確認が必要。
- **通知**：メール等の営業通知、Windows非起動時Push通知の実現性は未検証。通知送信基盤を決めるまで確定APIを作らない。
- **監査**：過度な個人情報・トークン・エラースタックの外部露出禁止。
- **運用**：開発・検証・本番を分離。元AIメモへの書込、既存設定・認証情報の閲覧、デプロイは別途承認が必要。
